# 新邮件缓存与按收件时间清理

## 用户要求与实际行为

- 收到收件箱新邮件后自动入队缓存正文和附件；与历史预热分开，新邮件上限 32 MiB，历史预热仍保留用户原有单封上限（默认 5 MiB）。
- 新队列独立连接、BODY.PEEK、64 KiB 分段和已确认断点；连续来信只追加，不重启正在下载的任务。前台读信或命令连接繁忙时暂停后续分段。
- 队列和发现水位一起持久化。首次启用建立当前基线；后续启动查询水位之后的全部 UID，覆盖关闭期间超过一页的新邮件。首次基线之前的旧信仍由历史预热处理。
- 每账户提供手动清理：7/30/90/180/365 天、自定义 1–36500 天或全部。先预览数量和磁盘占用，再确认清理；0 不是手动全部的别名。
- 每账户可设置自动保留期限，默认关闭，启动、设置变更及每小时检查；排队期间关掉或修改策略会撤销旧检查。
- 日期采用服务器 INTERNALDATE，完整原文头部和续传元数据中的收件时间，不使用打开时间或发件人 Date 头。按期限清理保留未知日期，全部清理包含可确认归属账户的未知日期项。
- 只删除本机原文、续传、内存正文及可确认归属的提取附件。服务器邮件、列表与搜索元数据、用户导出的附件和下载目录不删除。旧版孤立附件无法证明归属时保守保留。
- 清理截止时间持久化，历史预热、新信队列、相邻邮件预取共同遵守；显式重新打开可以再次下载。正在显示的正文保留，尚未返回的旧本地读取结果失效。

## 与下载缓慢问题的关系

原有缓存预热没有新信触发，且默认 5 MiB 上限跳过了 28.5 MiB 示例邮件。此前大邮件修复已完成正文先显示、图片附件按需下载、分段续传及无数据超时，详见 [大邮件下载排查](2026-11-01-large-mail-download.md)。本次将新邮件的完整缓存提前到到达后执行，不承诺改变邮箱服务器或网络链路的传输速率。

## 独立审查

用户要求独立 sub-agent review。另起两个未参与实现的只读 reviewer，分别审查后台和界面/附件，不以实现者自查替代。第一轮共发现 6 项 P2，修复后由原独立 reviewer 复核，均关闭，无剩余阻断发现。

| 独立发现 | 修复与回归证据 |
| --- | --- |
| 文字预览失败回退、慢缓存未命中后的下载可能取得清理后的新票据 | 票据绑定整个打开请求；Opening 和附件/引用/导出调用链复用同一 task-local 票据。测试文字预览 BAD → 清理 → 回退不回填 |
| 新信最终落盘被清理打断，却被当作已完成移出队列 | 仍允许缓存且没有完整文件时返回可重试失败；测试仅清理旧信时新信仍能重试落盘 |
| 长连接保留旧关闭设置，开启缓存后仍推进水位但不入队 | 同步入口持配置锁读取同接收代际的最新开关；测试关闭启动 → 开启 → 新 UID 持久入队 |
| 旧下载的迟到续传删除可能删除新下载断点 | 实际删除时重新在票据提交锁内校验；测试旧完成 → 清理 → 新断点 → 旧删除被拒 |
| 主读取返回迟到的本地快照可恢复已清理正文 | 主请求与旁路本地读取都校验清理代际；测试离线主读、在线降级本地两条路径 |
| 清理失败数按文件累加，界面却称为邮件数 | 按完整邮件身份去重；测试同封三个文件失败只计一封 |

独立审查不包含断电故障注入、Windows 原生界面或真实邮箱删除测试。
